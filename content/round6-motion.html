Twelve things move in Sorted. This page is all twelve, live, replayable, and slowed down twelve times if you want to see the frames. Everything here uses the tokens already locked in tokens.css — three curves, seven durations, no fourth anything.

How to use this page. Press things. Then set Slow-mo to 12× and press them again — most of these are 110–320ms and you cannot fairly judge them at speed. Then flip Reduced motion to ON and scroll the whole page again: nothing should break, nothing should disappear, and every state change should still be legible.

One decision is genuinely open and it is at the bottom, in section 12. Rounds 2 and 3 shipped a net-worth count-up you saw and did not object to. The approved brand kit now forbids it. I have built both, on the same figure, so you can settle it by eye rather than by rule.

01

The three curves

There is no fourth curve. If a component seems to need one, it is the wrong component. Each plot below is the real cubic-bezier from tokens.css, drawn from its control points — not an illustration of one. Press Run on any card and a 30px chip travels the track underneath it using that exact curve, with a dashed ghost travelling linear beside it for reference.

The counter-example — why rule 3 forbids ease-in

Both tracks below run for the same duration. The ease-in one feels slower, and that is not a metaphor — it delays movement through the first third of the animation, which is precisely the third the eye is watching hardest because it just clicked. On a login button pressed every morning, that reads as lag in the app, not style in the button.

When to use which

--ease-out — anything entering or exiting, and every press. This is the default; roughly 80% of Sorted uses it.
--ease-in-out — something already on screen changing position or size. In v1 that is exactly one thing: the budget bar re-scaling when a number changes.
--ease-drawer — reserved. Sorted's login and dashboard have no drawer or sheet in v1. The token exists because the deferred screens will, and because inventing it later would break the "three curves" claim.

Implementation
CSS  transition-timing-function. No GSAP anywhere in this section.
Why CSS
These are timing functions, not sequences. GSAP's power4.out is provided as an equivalent only for the one place a timeline is needed (§03).
02

The stamp press

The showpiece, because it is the one rule that came from you rather than from a style guide. Sorted's buttons have no hover state — the press is the entire feedback vocabulary of the primary CTA, so it has to be exactly right. Three buttons below: the shipped one, and the two ways it can be got wrong.

Or hold any button. At 1× the press is 110ms — you will not see it.
Shipped.stamp

translateY(2px) matched exactly to the 2px shadow offset, both properties on one curve. At every frame translate + offset = 2px, so the shadow's lower edge stays pinned and the button descends into the paper it was stamped on.

Neverscale() desync

Adds scale(.985). The box-shadow repaint and the GPU-composited scale run on different pipelines, so the 1.5px hard-edged border shrinks out of step with the shadow. At 12× the border visibly crawls inward while the shadow is still collapsing.

Nevershadow snap

Transitions transform only. The shadow snaps to zero on frame 1 — the silhouette jumps 2px shorter before the button starts moving, then the button drifts down to meet nothing. That flicker fires on every single press.

Duration
--dur-press · 110ms
Easing
--ease-out · cubic-bezier(.23, 1, .32, 1)
Properties
transform (translateY 0 → 2px) + box-shadow (0 2px 0 → 0 0 0). Nothing else.
Trigger
:active — pointer only. Never on keydown; a keyboard-submitted form does not animate its button (rule 1).
Implementation
CSS transition, not keyframes. A person can double-press a CTA faster than 110ms; a transition retargets from wherever it is, a keyframe restarts from zero.
Reduced
translate drops, shadow collapse survives. The state change stays legible with no movement.
Scope
Every component carrying --stamp. Today: pill, pill.sm, pill.fab. Any future stamp inherits this press.
/* tokens.css — ships as-is. Do not re-author this in a component. */

  box-shadow: var(--stamp);              /* 0 2px 0 var(--ink) */
  transition:
    transform  var(--dur-press) var(--ease-out),
    box-shadow var(--dur-press) var(--ease-out);
}
.stamp:active:not([disabled]) {
  transform:  translateY(var(--stamp-offset));   /* 2px — MUST equal the offset */
  box-shadow: var(--stamp-pressed);              /* 0 0 0 var(--ink) */
}

03

Login hero constellation

The one place in v1 that earns GSAP. Six chips, a core, and a dotted connector group that has to land in order — that is a sequence, not a state, and CSS animation-delay chains are brittle to interrupt. It plays once per page load and never loops (rule 14): a looping hero on a login screen reads as a spinner and tells the owner the app is stuck.

Animated layer dev control only — not in the product
Rule 15 · GSAP never loads this copy is untouched by JS, forever

Those two are the same asset. The right-hand one is assets/hero/constellation.svg exactly as authored; the left-hand one is that file with a GSAP timeline painted on top. If the CDN is slow, if the bundle splits badly, if someone blocks scripts — the login screen is still complete and still correct. That is rule 15, and it is the reason the entrance is a layer rather than an implementation.

Sequence
core scale .95→1 + fade (320ms) · connectors scale .72→1 from the core + fade (300ms, overlapped −140ms) · six chips scale .95→1 + fade, 46ms stagger (260ms each)
Total
~880ms wall clock. Every individual step is ≤320ms and so obeys rule 4; the total is a choreography, which rule 4 does not govern. It is also the only thing on screen and it happens once.
Easing
power4.out — the GSAP equivalent of --ease-out
Properties
transform (scale, via GSAP svgOrigin so each chip grows from its own centre and the connectors grow from the core at 210,190) + opacity. Nothing else.
Implementation
GSAP — the only GSAP in login + dashboard v1. Wrapped in gsap.matchMedia so reduced-motion gets an opacity-only variant automatically.
Loops
Never. once per mount, no repeat, no yoyo. Rule 14.
Reduced
opacity-only, 260ms, no stagger, no scale.
// components/login/HeroConstellation.tsx — React 18 + @gsap/react
import { useRef } from 'react';
import { useGSAP } from '@gsap/react';
import gsap from 'gsap';

export function HeroConstellation() {
  const root = useRef<SVGSVGElement>(null);

  useGSAP(() => {
    const mm = gsap.matchMedia();

    mm.add('(prefers-reduced-motion: no-preference)', () => {
      const chips = gsap.utils.toArray<SVGGElement>('.hc');
      // each chip grows from its own centre; svgOrigin beats transform-origin here
      chips.forEach(c => gsap.set(c, { svgOrigin: `${c.dataset.x} ${c.dataset.y}` }));
      gsap.set('.hero-links', { svgOrigin: '210 190' });   // the core

      const tl = gsap.timeline({ defaults: { ease: 'power4.out' } });   // --ease-out
      tl.from('.hero-core',  { scale: .95, opacity: 0, duration: .32, svgOrigin: '210 190' })
        .from('.hero-links', { scale: .72, opacity: 0, duration: .30 }, '-=.14')
        .from(chips,         { scale: .95, opacity: 0, duration: .26, stagger: .046 }, '-=.18');
      return () => tl.kill();
    });

    mm.add('(prefers-reduced-motion: reduce)', () => {
      // rule 10 — fewer and gentler, not zero. Opacity survives, movement does not.
      const tw = gsap.from('.hero-core, .hero-links, .hc', { opacity: 0, duration: .26 });
      return () => tw.kill();
    });

    return () => mm.revert();   // full cleanup on unmount
  }, { scope: root });

  return <svg ref={root} viewBox="0 0 420 380" /* …the static asset, inlined… */ />;
}

OTP stage transition

The real hinge of the login screen, and the most interesting genuine motion in the product. One panel, two stages: email, then the six-digit code. The user did not navigate — the same panel changed its mind — so the motion has to say replacement, not page change.

Step 1 · email

We'll send a six-digit code. It expires in 10 minutes.

Step 2 · code
Sent to om@sorted.in
407291

Six visual slots, one real input behind them — that is what keeps paste, autofill and screen readers working.

The decision that matters here is not the easing

It is that the panel does not change height. Stage 1 and stage 2 are absolutely positioned in a fixed-height box, so the CTA below never jumps and nothing reflows mid-transition. Height is not an animatable property in this system (rule 5) — so instead of animating it, the design removes the need to.

Direction carries meaning

Stage 1 leaves upward and stage 2 arrives from below: the same direction of travel, so it reads as one strip of paper moving up past a window rather than two unrelated fades. Going back reverses it exactly. Spatial consistency is the whole argument for animating this at all.

Enter
--dur-dropdown 200ms · --ease-out · opacity 0→1, translateY 8px→0
Exit
150ms (75% of enter, rule 9) · --ease-out · opacity 1→0, translateY 0→−6px
OTP slots
170ms each, 24ms stagger. Last slot completes at 120+170 = 290ms — deliberately under the 300ms ceiling.
Properties
opacity + transform only. Panel height is fixed, not animated.
Implementation
CSS transitions + transition-delay. Explicitly not GSAP: this is the login critical path and adding a 70KB dependency to fade two divs is the wrong trade. It also keeps the swap interruptible if the user hits Back mid-flight.
Reduced
translate drops, cross-fade survives at 180ms, stagger delays go to 0.

Focus rings

Tab through the form below, or use the stepper. Every ring is drawn outward with outline-offset: 3px so it lands on cream at 11.77:1. Drawn inward on the ink-filled CTA it would measure 1.37:1 — which is the same as not drawing it.

Shipped or press Tab
Never inset ring on an ink fill

Tab into this one. The input looks fine — cream background, plenty of contrast. The Verify button is where it falls apart: the ring is there, it is 2.5px, and you cannot see it.

shadcn's default ring-offset-background assumes a white page and produces exactly this. It must be overridden, not merely re-coloured.

Position · the ring does not animate

No fade, no scale, no draw-on. Focus is keyboard-initiated and a person traversing a form triggers it several times a second — rule 1 says anything seen that often gets nothing, and a ring that fades in at even 100ms reads as the app lagging behind the Tab key. It appears on the frame the focus lands. The only motion in this section is the stamp press, and that is pointer-only.

Duration
0ms. Instant, deliberately.
Properties
outline + outline-offset. Never box-shadow-as-ring on a filled control.
Contrast
--focus #14199C on --bg = 11.77:1 · on --ink = 1.37:1 (forbidden by construction)
Implementation
no animation — :focus-visible only, so a mouse press never draws a ring.

07

Chip row stagger

Rule 1 is the hardest rule in the kit because it argues against the fun thing. Sorted is opened every morning by one person. The chip rail is the first thing on screen and it is the same six chips every single time. So the honest question is not "what stagger interval" — it is "why is this animating at all".

Position · two different lists, two different answers

The sidebar chip rail does not animate. At all. Six fixed items, identical on every load, seen more than a hundred times a week by the one person who uses this. Rule 1 is unambiguous and there is no counter-argument: an 80ms stagger on the navigation of a daily tool is 480ms of the owner waiting for their own sidebar.

The budget rows do animate — opacity only, 24ms apart. Not for delight. They are replacing a skeleton, and a skeleton that swaps to real content on a single frame reads as a glitch rather than as an arrival. That is rule 2's "preventing a jarring change", which is a legitimate reason. There is no movement: the rows are already in their final position under the skeleton, so translating them would invent motion that did not happen.

Compare the two right-hand demos above at 4×. The 40ms and 80ms versions look better in a gallery and worse in a product — they announce themselves, and the announcement is "the app is still getting ready", which on a dashboard is precisely the wrong message.

Sidebar rail
no animation · 0ms · rule 1
Budget rows
CSS · 200ms --ease-out · opacity 0→1 only · 24ms stagger · fires once, on the skeleton→data swap
Ceiling
4 rows × 24ms + 200ms = 272ms. Under 300 by construction; if the module ever renders more than 6 rows the stagger caps rather than growing.
Reduced
Stagger to 0, cross-fade survives. Identical to the non-reduced version minus the offsets.
/* opacity only. If the row is not moving, do not translate it. */
.budget-row {
  animation: row-in 200ms var(--ease-out) both;
  animation-delay: calc(min(var(--i), 5) * 24ms);   /* caps, never grows unbounded */
}
@keyframes row-in { from { opacity: 0 } to { opacity: 1 } }

@media (prefers-reduced-motion: reduce) { .budget-row { animation-delay: 0ms } }

/* the sidebar rail gets nothing. This is intentional and it is the rule. */

Position · the tether is static, with one exception that is not the tether's

It is a provenance mark, closer to a watermark than to a control. Skeleton & loading

The chip-rhythm skeleton. It is not a grey rectangle field — it reproduces the exact row grid (30px chip gutter, 1fr name, auto amount) with a dashed circle in column one, so when the data lands nothing reflows by a single pixel and the eye does not have to re-find the column it was already reading.

Budget vs Spend · loading
Food & groceries₹9,240
Bills & utilities₹5,120
Transport₹2,410
Shopping₹3,900
Why a keyframe here and nowhere else

Rule 8 says transitions, not keyframes, for anything a person can trigger twice quickly. A skeleton is the opposite: nobody triggers it, it loops until the data lands, and it has no interruptible state to retarget to. A keyframe is correct here because it is not user-driven — and it is the only keyframe in login + dashboard v1.

Why the dashed circle

A filled grey circle in the chip gutter would be a lie about which chip is coming — and under the chip taxonomy, a coloured circle is meaning. Dashed says "a chip goes here and I don't know which yet", which is exactly true.

Duration
--dur-skeleton 1150ms, infinite alternate
Easing
--ease-in-out · cubic-bezier(.77, 0, .175, 1)
Property
opacity .34 → .72 → .34. No shimmer sweep, no gradient, no transform — Sorted has no gradients and a sweeping highlight would be the only faked light source in the product.
Rhythm
140ms row offset. The rows breathe out of phase, which is what makes it read as a list rather than as one flashing block.
Swap
skeleton → data is an opacity cross-fade at 200ms --ease-out with the 24ms row stagger from §07. No layout change, because the grids are identical.
Implementation
CSS keyframe, the one exception to rule 8.
Reduced
Pulse stops entirely and holds at opacity .5. A repeating pulse is the single most nauseating thing on a loading screen for a motion-sensitive user, and a static skeleton communicates "loading" perfectly well.
@keyframes chip-pulse { 0%, 100% { opacity: .34 } 50% { opacity: .72 } }

@media (prefers-reduced-motion: reduce) {
  .skeleton { animation: none; opacity: .5; }   /* hold, do not pulse */
}

Press it twice quickly. The notice pushes 64px of layout down while you are still reaching for the button — a mis-click waiting to happen, and no easing curve fixes it. Most "bad animation" is bad layout.

Position

The notice animates, and the reason is rule 2's "preventing a jarring change" plus one specific product fact: a wrong OTP is the moment the owner is most likely to think the app is broken rather than that they mistyped. A notice that appears reads as a response; a notice that is suddenly just there reads as a page that reloaded. 200ms is enough to say "this is new" and short enough that it never delays reading it.

The count-up, and rule 12

This is the one thing on this page I am not deciding for you. Rounds 2 and 3 both shipped a GSAP net-worth count-up with correct lakh/crore grouping. You saw it and did not object. The figure has exactly two states: not yet known (a skeleton, honestly shaped like the number) and known (the number). There is no third state where it is partly known, because there is no such thing as partly knowing your net worth.

The argument for rule 12, stated honestly

A count-up displays a wrong balance to the person who owns that money for the entire duration of the animation. At 900ms, someone glancing at their phone at 7am sees ₹18,40,220 for a quarter of a second when the real figure is ₹47,82,610. Nothing bad happens — but the interface has told them something untrue in order to look nice, and this is the one product category where that trade is worst.

The second argument is duration in the other sense. By day three the novelty is gone and only the delay is left. This is a tool opened every morning by one person. Everything on this page that survived did so by passing rule 1 — "anything seen a hundred times a day gets no animation" — and the net-worth figure is the single most-looked-at pixel in the product. The count-up is the one element that fails that test hardest, and it is also the one that would be most fun to keep.

And a third, quieter one: if GSAP fails to load, version B is already correct and version A is a blank number until the fallback fires. Rule 15 and rule 12 are the same argument wearing different clothes.

The argument for overruling it

You have already seen it twice and liked it enough to keep going. Net Worth is the "number you admire" in the locked hierarchy — it is explicitly not the number that changes behaviour, that is Guilt-Free Money at 108px. If any figure in this product can afford a moment of drama, it is precisely this one, because nobody makes a decision off it. A narrower version of the rule is available: rule 12 applies to every rupee figure except Net Worth, count-up capped at 600ms, once per session rather than on every re-render, skipped entirely under reduced motion.

I am not recommending that. I am saying it is defensible, and that the decision is yours rather than the brand kit's, because the brand kit made it without asking.
