§ 02

What the hero does at stage 2 — the position, and the argument

The brief asked for a call. Here it is, with the reasoning, because this is the only genuinely interesting motion decision on the screen.

It persists. It does not transform.

The illustration holds its exact position and geometry across the stage change. No chip moves, nothing scales, nothing fades, no colour changes, and the hero does not replay. The stage change is carried entirely by the form column.

The reason is the moment itself. At stage 2 the owner is holding a phone in one hand, reading six digits off a mail app, and typing them with the other. That is the highest attention cost in the whole product. Moving the largest object on screen at precisely that moment is the worst possible place to spend motion budget. Rule 1 — anything seen a hundred times a day gets no animation — bites here harder than anywhere.

A transforming hero would also fight rule 14. A hero that re-animates on a state change has, from the user's seat, played twice; the second play arrives while they are waiting for an email, which is exactly when a moving illustration starts reading as a spinner and implying the app is stuck.

Except for one gesture, which is free.

The hero makes a single response: the six dotted connectors advance their dash pattern inward by exactly one dash cycle — 10 user units, stroke-dashoffset: -=10 — over 320ms on --ease-in-out, staggered 30ms, once, and stop. Nothing else in the SVG is touched.

It reads as the dotted line having travelled: a code left, and came back. That meaning is already loaded into this exact stroke — the same 1.6px, dash 4 6, round-capped line is the tether, whose whole job in the product is to say “a connection did this, not you.”

The reason it is safe is arithmetic. The dash pattern is periodic with a cycle of 10. Advancing by exactly one full cycle means the end frame is pixel-identical to the start frame. So the gesture has no state: skip it under reduced motion, skip it with JS off, skip it on a slow first paint — the screen is byte-for-byte correct either way. A motion whose final frame equals its first frame can never become a dependency, and can never leave the illustration stranded mid-flight if the tab is backgrounded.

Precedent: stroke-dashoffset is already the sanctioned exception to rule 5 in this system — the brand-kit README specifies “a dashoffset draw that must land in order” as part of the hero entrance. It is paint-only on an SVG and triggers no layout.

Rejected alternatives, and why

ConsideredRejected because
Hero recedes — fades to 40%, form takes focus Dimming the only warm thing on the screen at the moment the user is most likely to get stuck is the wrong emotional direction, and a persistent 40% illustration looks like a rendering failure rather than a decision.

It is a Flip animation across a 762px gap — expensive, hard to interrupt, impossible to degrade, and it would have to reverse correctly on “use a different address”. § 03

Stage 1 · submitting and error

Form column at 1:1. The hero is unchanged in all of these, which is the point — cropping to the column is itself the argument.

The submitting button is not dimmed. The house .pill[disabled]{opacity:.55} was dropped here on purpose: the button you are waiting on is the button you are reading, and dropping cream-on-ink to 55% takes 16.08:1 down to roughly 4:1 at exactly the wrong moment. Instead the button holds itself pressed — translated the full --stamp-offset with the shadow collapsed to zero. The silhouette is 2px shorter and flat against the paper. That reads as “held down” from across the room, at full contrast, and it reuses the press vocabulary the user just triggered rather than inventing a disabled vocabulary.

Why the button disappears instead of dimming

A greyed-out button is still a button. It still invites a click, still gets clicked, and still teaches nothing about why the click failed. When an action is genuinely unavailable for a known duration, Sorted stops drawing a button and draws a clock — mono, uppercase, --dim, no border, no fill, no stamp, nothing to press.

This is the same component that governs resend at stage 2, and it is the single most important design decision on this screen. The countdown is a live string, so it uses --dim legitimately: mono micro-label, uppercase, 0.13em tracking, glanced rather than read. The sentence above it — which contains verbs — is --dim-2 at 5.71:1. That split is the shipped test.

Note the rate-limit copy names a wall the user cannot see and a time they can act on. “Please try again later” would have been the same information with the useful half removed.

The double-submit guard, designed rather than disabled

A second OTP request invalidates the code already in the inbox. To the owner that does not read as “I requested twice” — it reads as “Sorted emailed me a broken code.” The guard exists to prevent a bug report about a bug that isn't there.

Three separate moves defend it, in order of how early they catch the mistake:

MoveWhat it doesWhy it's placed there
The warning is up front Stage 1 idle already says “asking for a second one kills the first”. Cheapest possible intervention: the user learns the rule before they can break it, at a moment when they have nothing else to read.
Resend is a clock, not a button Until the code expires there is no pressable element at all — just NEW CODE IN 9:12 beside a clock glyph. You cannot double-submit an affordance that hasn't been drawn. A disabled button would still be clicked, and a disabled button with a tooltip is a design apologising for itself.
Submit holds itself pressed During Sending… / Verifying… the pill sits translated 2px with the shadow flat, and the surrounding fieldset is inert. Covers the impatient double-click on the primary action, which is the other way to fire two requests. Full contrast retained — see § 03.

“Different address” stays live throughout. It is the one escape hatch that is never dangerous — it abandons the current code rather than racing it — and without it the clock would be a trap for the one case that matters: a typo in the email.

§ 06

Keyboard focus — and a finding

Every focusable thing on this screen, with its ring drawn where it is actually drawn. One correction to the round-3 field CSS is folded in here.

Finding: the round-3 field ring reproduced the forbidden adjacency

Round 3 shipped .fld:focus{box-shadow:0 0 0 2.5px var(--focus)}. That ring has zero offset, so 2.5px of #14199C sits flush against the field's own 1.5px #1A1A1A border. The locked measurement for that pair is 1.37:1 — the exact adjacency the focus-ring rule was written to forbid. It passed review because the field is transparent rather than ink-filled, so the letter of the rule ("never box-shadow-as-ring on a filled control") did not catch it. The border is the filled part.

Corrected everywhere on this screen: outline: 2.5px solid var(--focus); outline-offset: 3px. The ring clears the ink border by 3px of cream and measures 11.77:1. Outlines follow border-radius in every browser this app targets, so it wraps the 999px pill correctly. This also applies to the OTP slots, which round 3 gave the same zero-offset treatment.

Tab order

Stage 1: email → Send code. Two stops. There is nothing else on the column and nothing focusable in the hero — the illustration is role="img" with a title and desc, not a set of tabbable nodes.

Stage 2: the OTP group (one stop — one real input behind six slots) → Verify → Different address. The resend clock is not in the order while it is a clock, and enters it as a normal button the instant it becomes one.

Focus moves to the OTP input automatically on the stage change, and to the notice on error. Rings do not animate — rule 1, applied to keyboard traversal.

§ 07

JavaScript disabled

Rule 15, tested rather than promised. This is the same markup with GSAP removed and every script blocked.

Nothing on this screen starts hidden in CSS. There is no opacity:0 waiting for a hydration flag, no data-mounted gate, no visibility:hidden on the hero group. The entrance is built entirely with gsap.from(), which reads the final state off the DOM and paints a temporary from-state on top of it — so if the script never runs, the browser has already drawn the finished illustration. The hero SVG is a complete asset that happens to be animatable, in that order.

What survives without JS

The hero, in full. The layout, the type, the focus rings, the stamp press (CSS :active), the skeleton pulse, and every error notice that was server-rendered.

Both stages are real <form> elements with method and action set, so the recommendation is to drive them with a server action rather than a fetch in an onSubmit. Stage 2 then becomes a fresh server render of the same route, errors arrive as props, and the whole screen works with scripting off.

What doesn't, and why that's acceptable

The live countdown freezes at whatever the server rendered. That is fine — the copy states an absolute time (“good until 9:14”) alongside the relative one, so the absolute figure carries the meaning on its own.

The dash gesture and the entrance don't play. Both were designed to be droppable: the entrance because gsap.from() leaves the final frame in place, the gesture because its final frame equals its first.

OTP paste-detection and iOS SMS autofill degrade to typing six digits. Nothing is unreachable.

§ 08

Mobile · 390 × 844

The owner will open this on a phone more often than on a desktop, because the code arrives on the phone. This is not a scaled-down desktop.

Three changes, all forced by the device rather than chosen. The split becomes a stack — the hero-field panel keeps its ink border and 26px radius but sits as a block at the top, with the constellation cropped to 186px tall so the form clears the keyboard. The OTP slots shrink to 48×56 with an 8px gap: six at 52 plus five 10px gaps is 362px, which does not fit inside 390 minus two 20px margins; 48/8 gives 328px and 11px of air either side. The field stays at 16px — --type-input exists precisely so iOS never zooms the viewport on focus, which is the single most common mobile login defect.

§ 09

Implementation

The exact code an engineer writes in the Next.js app, and what shadcn does and does not give you here.

The hero — the one GSAP dependency in v1

Client component, useGSAP scoped to the container so cleanup is automatic on unmount. Everything is gsap.from(), never gsap.set() to zero, so the DOM's own state is the final frame. matchMedia carries the reduced-motion branch — fewer and gentler, not nothing.

// web/app/login/HeroConstellation.tsx
'use client';
import { useGSAP } from '@gsap/react';
import gsap from 'gsap';
import { useRef } from 'react';

export function HeroConstellation({ stage }: { stage: 'email' | 'code' }) {
  const root = useRef<SVGSVGElement>(null);

  /* ── entrance · plays exactly once, on mount ─────────────────────── */
  useGSAP(() => {
    const mm = gsap.matchMedia();

    mm.add('(prefers-reduced-motion: no-preference)', () => {
      // dashoffset needs a measured length; do it once, here.
      const links = gsap.utils.toArray<SVGPathElement>('#hero-links path');
      links.forEach(p => { p.dataset.len = String(p.getTotalLength()); });

      gsap.timeline({ defaults: { ease: 'power4.out' } })
        .from('#hero-core', { opacity: 0, scale: .96, duration: .42 })
        .from(links, {
          strokeDashoffset: (i) => Number(links[i].dataset.len),
          opacity: 0, duration: .38, stagger: .045, ease: 'power3.out',
        }, '-=.24')
        .from('.hc', { opacity: 0, scale: .94, duration: .42, stagger: .055 }, '-=.30');
    });

    mm.add('(prefers-reduced-motion: reduce)', () => {
      // gentler, not zero: opacity only, no scale, no draw.
      gsap.from('#hero-core, .hc', { opacity: 0, duration: .2, stagger: .03 });
    });

    return () => mm.revert();
  }, { scope: root });          // no deps — mount only. Rule 14.

  /* ── the stage gesture · one dash cycle, once per transition ──────
     dasharray is `4 6`, so the cycle is 10. Advancing by exactly -10
     leaves the final frame identical to the first, which is why this is
     safe to skip entirely under reduced motion or with JS off.        */
  useGSAP(() => {
    if (stage !== 'code') return;
    if (window.matchMedia('(prefers-reduced-motion: reduce)').matches) return;
    gsap.to('#hero-links path', {
      strokeDashoffset: '-=10',
      duration: .32,               // --dur-drawer
      ease: 'power4.inOut',       // --ease-in-out
      stagger: .03,
      overwrite: 'auto',          // retarget if the user bounces stages
    });
  }, { scope: root, dependencies: [stage] });

  return <svg ref={root} viewBox="0 0 420 380" role="img" …>{/* the asset, inlined verbatim */}</svg>;
}

Three traps in that file

1 · Never gsap.set(…, {opacity:0}) at module scope or in a layout effect. It creates a window where the hero is invisible before the timeline starts, and if the timeline throws it stays invisible. from() is atomic — it writes the start state and the tween in the same tick.

2 · transform-box: fill-box is required on .hc and #hero-core or the scale happens about the SVG viewport origin and every chip flies in from the top-left. One CSS line, easily lost.

3 · getTotalLength() must run after layout. Inside useGSAP it does. Called during render it returns 0 and the draw silently no-ops.
